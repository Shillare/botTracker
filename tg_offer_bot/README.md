# tg_offer_bot — Telegram-бот для продажи NFT-подарков за Telegram Stars

Production-ready бот на **aiogram 3.31** / **Python 3.11+** с полной поддержкой
**Business Connection** (отправка и редактирование сообщений от имени
бизнес-аккаунта), SQLite-хранилищем, админ-панелью и premium-эмодзи.

## 3. Подключение к бизнес-аккаунту

1. Откройте **Telegram → Настройки → Бизнес** (доступно только у Telegram Premium
   и только на десктопе/мобильном клиенте с актуальной версией).
2. **Подключить аккаунт → введите username вашего бота** и выдайте права:
   - «Отправлять сообщения» — обязательно, без него `business_connection_id` не работает;
   - «Читать сообщения» — рекомендуется;
   - «Передавать и улучшать подарки», «Передавать Stars» — если планируете
     автоматизировать передачу подарков.
3. Бот получит апдейт `business_connection` с `is_enabled=True`, сохранит
   `business_connection_id` в таблицу `business_connections` и напишет вам
   в личку подтверждение. В логах появится:

```
Бизнес-аккаунт ПОДКЛЮЧЁН: @ivan, connection_id=BQ1234567890, права: reply, transfer_gifts
```

4. При отключении придёт `business_connection` с `is_enabled=False` — бот пометит
   запись неактивной и **перестанет** подставлять этот `business_connection_id`
   в исходящие сообщения:

```
Бизнес-аккаунт ОТКЛЮЧЁН: @ivan, connection_id=BQ1234567890
```

### Как работает проброс `business_connection_id`

`BusinessContextMiddleware` определяет его для каждого апдейта:

1. `message.business_connection_id` — если апдейт пришёл в чат бизнес-аккаунта;
2. `callback_query.message.business_connection_id` — при нажатии кнопки;
3. проверка по БД: если подключение отключено — значение отбрасывается;
4. `DEFAULT_BUSINESS_CONNECTION_ID` из конфигурации.

Дальше значение попадает в `data["business_connection_id"]` и передаётся
в `bot.send_message(...)` / `bot.edit_message_text(...)`.

> **Важно:** `business_connection_id` обязателен и при редактировании сообщения,
> отправленного от имени аккаунта. Без него Telegram отвечает `400 Bad Request:
> message to edit not found`.

## 4. Premium-эмодзи (custom emoji)

### Как вставить в текст

```html
<tg-emoji emoji-id="5985472565508838112">✅</tg-emoji>
```

Символ внутри тега (`✅`) — это **fallback**: его покажут клиенты без поддержки
premium-эмодзи. Он обязателен, иначе клиент отобразит пустоту.

В коде это вынесено в хелперы:

```python
from app.utils.text import tg_emoji

tg_emoji("5985472565508838112", "✅")
# '<tg-emoji emoji-id="5985472565508838112">✅</tg-emoji>'
```

Все используемые ID собраны в `app/constants.py`:

```python
EMOJI_ACCEPT    = "5776375003280838798"   # ✅ Принять
EMOJI_DECLINE   = "5778527486270770928"   # ❌ Отклонить
EMOJI_GIFT      = "6032937473162614352"   # 🎁 подарок продан
EMOJI_ACCEPTED  = "5985472565508838112"
EMOJI_DECLINED  = "5260342697075416641"   # отклонено
EMOJI_ICON_PRIMARY = "5285430309720966085"
EMOJI_ICON_SUCCESS = "5310076249404621168"
EMOJI_ICON_DANGER  = "5310169226856644648"
```

### Кто должен иметь Telegram Premium

С версии Bot API 9.4 боту **не нужно** покупать юзернейм на Fragment: достаточно
Telegram Premium у **владельца** бота. Работает в личных чатах, группах и
супергруппах. Если премиума нет, Telegram отклоняет запрос — бот не падает,
а автоматически снимает оформление (см. ниже).

### Эмодзи на кнопках: `icon_custom_emoji_id` + `style`

Bot API 9.4 добавил в кнопки два необязательных поля:

| Поле | Значения | Смысл |
|---|---|---|
| `style` | `danger` / `success` / `primary` (или пусто) | Цвет кнопки |
| `icon_custom_emoji_id` | id премиум-эмодзи | Иконка слева от текста |

```python
InlineKeyboardButton(
    text="Принять",
    callback_data=offer_id,
    style="success",
    icon_custom_emoji_id="5776375003280838798",
)
```

Текст кнопки при этом **не поддерживает HTML** — иконка задаётся отдельным полем,
а не тегом `<tg-emoji>`.

### Что делает шлюз, если фича не поддержана

`TelegramGateway` на ошибку `BUTTON_CUSTOM_EMOJI_INVALID` или
`Invalid button style specified` снимает **ровно то поле, на которое указывает
Telegram**, сохраняя цвет/иконку по возможности и никогда не теряя действие
кнопки (`callback_data`/`url`):

1. `BUTTON_CUSTOM_EMOJI_INVALID` → исчезает иконка, кнопка остаётся цветной;
2. `Invalid button style specified` → исчезает цвет, иконка остаётся;
3. если не поддержаны обе → остаётся обычная кнопка с текстом;
4. если проблема в HTML (а не в кнопке) → отказ от разметки.

Проверено тестами `scenario_gateway_errors`. Это страховка для self-hosted
`bot-api` на версии ниже 9.4 и для бота без Telegram Premium у владельца.

### Как узнать `emoji_id`

**Способ 1 — чистый Bot API (без MTProto).** Custom emoji приходят в апдейте как
сущности с типом `custom_emoji`:

```python
@router.message()
async def dump(message: Message) -> None:
    for entity in message.entities or []:
        if entity.type == "custom_emoji":
            print(entity.custom_emoji_id)
```

Как получить такой апдейт: перешлите любой чат с premium-эмодзи вашему боту
(`/start` у @userinfobot или просто пересылка в диалог с ботом) — бот получит
`Message` с `entities[].custom_emoji_id`.

**Способ 2 — через бота.** Отправьте боту любое сообщение с premium-эмодзи,
затем выполните в коде тот же дамп сущностей.

**Способ 3 — MTProto (Telethon/Pyrogram)**, если нужно массово:

```python
msg = await client.get_messages("t.me/username", ids=42)
for e in msg.entities:
    if isinstance(e, MessageEntityCustomEmoji):
        print(e.custom_emoji_id)
```

**Способ 4 — вручную.** Telegram Desktop: ПКМ по эмодзи → «Копировать» → в
`<tg-emoji emoji-id="...">`. Работает не во всех версиях клиента.

### Premium-эмодзи на кнопках

Текст кнопки **не поддерживает HTML**. Для иконки используется отдельное поле:

```python
InlineKeyboardButton(
    text="Принять",
    callback_data="of:a:<offer_id>",
    icon_custom_emoji_id="5776375003280838798",
    style="success",
)
```

`style` (`danger` / `success` / `primary`) появился в Bot API 9.0 и цветёт саму
кнопку: красный / зелёный / синий.

> **Ограничение:** `icon_custom_emoji_id` доступен ботам, которые купили доп.
> имена на Fragment, либо работает, если у владельца бота есть Telegram Premium.
> Без этого Telegram отклонит запрос. Поэтому `TelegramGateway` автоматически
> деградирует: сначала убирает `style` и иконки, затем — HTML. Кнопка остаётся
> рабочей, просто без оформления.

## 5. Команда `benz`

### Формат

```
benz <ссылка на NFT> <цена> <валюта> [@username]
```

Примеры:

```
benz https://t.me/nft/ViceCream-382938 2500 Stars
benz t.me/StarNotepad-21211 1.5k Gram
benz https://t.me/nft/Gift-9999 2 500 Stars
benz https://t.me/nft/Gift-9999 100 Gram @buyer
```

- **Валюта** — `Stars` (по умолчанию, если опущена), `Gram`, `TON`, `USDT`.
  Регистр не важен, алиасы: `star`, `xtr`, `звёзд` → `Stars`.
- **Цена** — `2500`, `2 500`, `2,500`, `1'000`, `2.5k`, `1.2к`, `1.5m`.
- **`@username`** — необязательный получатель подарка. Если он указан, кнопка
  «Передать» сразу откроет передачу именно ему. Без него бот берёт username
  того, кто нажал «Принять», а если у того нет публичного username —
  значение `TRANSFER_RECIPIENT_USERNAME` из `.env`.

Команда работает **в любом чате**: личный диалог, группа, супергруппа — везде,
где бот подключён к бизнес-аккаунту. Команда пишется **без точки**: `benz`.
Точка и слэш остались необязательными (`.benz`, `/benz`), регистр не важен,
есть вариант с `@имя_бота` (`benz@MyBot ...`).

> **Кто может вызвать `benz`.** По умолчанию — только владелец подключённого
> бизнес-аккаунта (`ONLY_BUSINESS_OWNER_COMMANDS=true`). В группе команду может
> набрать любой участник, а отвечать бот будет от имени аккаунта, поэтому чужие
> команды молча игнорируются. Без бизнес-подключения правило не действует —
> там `benz` работает как обычная команда бота.

### Жизненный цикл

| Шаг | Что происходит |
|---|---|
| `benz <ссылка> <цена> <валюта>` | Валидация ссылки и цены, запись в БД со статусом `pending`, отправка карточки, удаление сообщения с командой |
| Кнопка «Принять» | Атомарный переход `pending → accepted`, карточка редактируется, появляется кнопка «Передать» |
| Кнопка «Отклонить» | Переход `pending → declined`, карточка редактируется, клавиатура снимается |
| Повторное нажатие | Ничего не меняется, всплывает тост «Это предложение уже обработано» |

### Защита от повторного нажатия

Не «счётчик в памяти», а compare-and-set на уровне SQL:

```sql
UPDATE offers
   SET status = ?, resolved_at = ?, resolved_by = ?
 WHERE id = ?
   AND status = 'pending'
   AND (expires_at IS NULL OR expires_at > ?)
```

Возвращается `rowcount`. Ровно один обработчик получает `1` и редактирует
сообщение; все остальные получают `0` и показывают тост. Это работает даже при
50 одновременных нажатиях — проверено тестом `test_race_condition`.

То же условие `expires_at > now` автоматически запрещает принятие
просроченного предложения.

### Язык карточки

Язык задаётся последним аргументом команды:

```
benz https://t.me/nft/StarNotepad-21211 2500 Stars      # русский
benz https://t.me/nft/StarNotepad-21211 2500 Stars EU   # английский
benz https://t.me/nft/StarNotepad-21211 2.5k Gram ar    # арабский
benz https://t.me/nft/StarNotepad-21211 2500 Stars @buyer ar
```

- алиасы: `EU` / `en` / `eng` / `english` → английский, `ar` / `arb` / `arabic`
  → арабский, `ru` → русский;
- без суффикса берётся `DEFAULT_LANGUAGE` из `.env`;
- язык сохраняется в предложении, поэтому карточка «продан», тосты,
  уведомление продавцу и тексты ошибок всегда на том же языке, что и карточка.

Переведено всё, что видит покупатель: текст карточек, подписи кнопок
(Принять / Отклонить / Передать), тосты, объяснения ошибок и справка `/help`.
Кнопки на арабском: **رفض** (отклонить) и **قبول** (принять).

Русский вариант сохраняет гомоглифы в словах (`Пoльзoвaтeль`, `зa подapoк`) —
они обходят строковый антиспам-фильтр Telegram. Подпись валюты, наоборот,
обычная: `Stars` читается без омоглифов. В английском и арабском весь текст
обычный. Длительность переводится: `5ч 59м` / `5h 59m` / `5س 59د`.

Все строки лежат в `app/i18n.py` — по одном объекте `Lang` на язык.

## 6. Роли доступа

| Роль | Кто это | Что может |
|---|---|---|
| **Владелец** | `OWNER_IDS` в `.env` | Всё, что может админ, **плюс** выдача и снятие прав |
| **Админ** | таблица `admins` | Пользуется ботом: карточки, кнопки, `/help`, `benz` |
| **Остальные** | — | Бот их полностью игнорирует |

### Команды (только владелец)

| Команда | Действие |
|---|---|
| `/admins` | Список админов; владельцы помечены 👑 |
| `/add_admin <user_id>` | Выдать права |
| `/remove_admin <user_id>` | Снять права |
| `/business_status` | Бизнес-подключения и выданные права |

Назначенный админ этими командами **не может** пользоваться — вместо отказа
он получает явное сообщение «Только для владельца». Молчание тут вводит в
заблуждение: человек думает, что команда неверна.

Владельца нельзя разжаловать, иначе бот можно «замуровать» навсегда.
Страховка «нельзя снять последнего админа» работает только когда
`OWNER_IDS` не задан: владелец всегда админ, поэтому снять всех админов из БД
безопасно.

### Как сменить владельца

1. Прописать новый ID в `OWNER_IDS` в `.env`.
2. Запустить `python tools/reset_owners.py` — скрипт снимет права со всех, кого
   нет в `OWNER_IDS`, и отключит оставшиеся бизнес-подключения прежних
   владельцев.

Сам по себе `.env` недостаточен: прежние ID остаются в таблице `admins`, и бот
продолжит считать их админами. Таблица `business_connections` тоже помнит
прежнее подключение — его нужно отключить, иначе апдейты от старого аккаунта
продолжат обрабатываться.

### Гейт не-админов

`AdminGateMiddleware` обрывает обработку **до** роутеров: ни ответа в чат,
ни записи в БД, ни реакции на подключение бизнес-аккаунта.

```python
resolved = event.event if isinstance(event, Update) else event
if isinstance(resolved, (Message, BusinessConnection)) and not data["is_admin"]:
    return None
```

Два важных нюанса:

- гейт смотрит на `Update.event`, а не на сам `Update`: в outer-middleware
  aiogram отдаёт сырой апдейт, а не разрешённое событие;
- **нажатия inline-кнопок гейт не трогает.** «Принять» жмёт покупатель, а он
  не обязан быть админом — иначе предложение нельзя было бы закрыть.

Владелец всегда админ даже без записи в таблице `admins`, поэтому потерять
доступ к боту через `/remove_admin` невозможно.

## 7. Примеры оформления сообщений

### Новое предложение

```html
Пoльзoвaтeль <b>Анна</b> пpeдлaгaeт Baм <b>2500 Ѕtarѕ</b> зa подapoк
<a href="https://t.me/nft/SantaHat-3438">Santa Hat #3,438</a>

Пreдлoжeниe дeйcтвyeт ещё <b>5ч 59м.</b>
```

Ссылка на подарок — единственная в тексте, поэтому Telegram рисует предпросмотр **над текстом** (`link_preview_options.show_above_text=true`).

Ник берётся из профиля (`first_name last_name`), а не из `@username`; кавычек нет ни у ника, ни у суммы.

Название подарка — гиперссылка на страницу подарка (`<a href="...">…</a>`), разделитель разрядов в номере — запятая, как в интерфейсе Telegram. Внутри `<a>` нет вложенного `<b>`: разметка в ссылке избыточна и по-разному отображается у клиентов без поддержки HTML.

Смена валюты меняет только подпись:

```html
Пoльзoвaтeль <b>Анна</b> пreдлaгaeт Baм <b>100 Gram</b> зa подapoк
```

Кнопки слева направо: **Отклонить** (`icon_custom_emoji_id=5778527486270770928`)
и **Принять** (`5776375003280838798`). Цвет (`style`) не используется — кнопки
оставлены с премиум-иконками, но без заливки.

> **У автора кнопки не работают.** Карточка адресована покупателю, поэтому
> у того, кто отправил `benz`, «Принять» и «Отклонить» не реагируют: сообщение
> не меняется, в БД статус остаётся `pending`, а по нажатию всплывает
> «Это ваше предложение. Кнопки «Принять» и «Отклонить» работают у покупателя».
> Исключение — обычный диалог с ботом без бизнес-подключения: там карточка
> приходит тому же человеку, который её создал, и кнопки работают у него.
> Поведение переключается политикой `ACCEPT_POLICY`.

> **Почему в исходнике «кривые» буквы.** В карточке часть латинских букв
> намеренно заменена кириллическими омоглифами (`Пoльзoвaтeль`, `зa подapoк`,
> `Viсе Crеам`) — строковые фильтры Telegram такой текст не распознают, а
> клиент отрисовывает его как обычный. Наборы слов лежат в `app/constants.py`
> (`H_*`) и `app/utils/text.py` (`obfuscate`). Подписи кнопок и валюты
> (`Stars`) оставлены обычными: подпись кнопки видна сразу при нажатии, и
> подмена бросается в глаза, а на антиспам она не влияет.

Сообщение с самой командой (`benz t.me/nft/StarNotepad-21211 100 Gram`)
удаляется сразу после отправки карточки — у обоих участников чата. Отключается
флагом `DELETE_COMMAND_MESSAGE=false`.

> **Права на удаление.** Если апдейт пришёл по бизнес-подключению, бот удаляет
> сообщение через `deleteBusinessMessages(business_connection_id, message_ids)`.
> Без подключения используется `deleteMessage` — там нужны права на чат.
> Если прав нет, бот запишет ошибку в лог и продолжит: карточка останется
> на месте, работа не сломается.

### После принятия

```html
<tg-emoji emoji-id="5875180111744995604">🎁</tg-emoji> Подapoк: <a href="https://t.me/nft/SantaHat-3438">Ѕanta Ηat #3,438</a> ycпeшнo пpoдaн!

<b>• Пepeдaйтe подapoк пoкyпaтeлю для зaчиcлeния Stars.</b>
```

Название с номером — единственная ссылка в сообщении, поэтому Telegram рисует
предпросмотр подарка **над текстом** (`link_preview_options.show_above_text=true`).
Кавычек и даты больше нет.

Две мелочи оформления, которые видно в этой же карточке:

* подпись `Подарок` с большой буквы — это начало строки, а не продолжение
  предложения (в объявлении та же гомоглифная строка стоит строчной: `зa подapoк`);
* инструкция **жирная**: это единственное, что продавец обязан сделать дальше,
  и на мобильном её нельзя пропустить.

Под ней — одна кнопка **Передать** (`tg://send_gift?to=anna`) без цвета и
без иконки. Кнопка «Как передать» появляется, только если заполнен
`HOW_TO_TRANSFER_URL`.

> **Подпись валюты и `PEER_FLOOD`.** Telegram режет сообщение от имени
> бизнес-аккаунта с `PEER_FLOOD`, если получатель никогда не писал боту, а в
> тексте встретилась подпись валюты вместе с внешней ссылкой. Измерено на
> реальном аккаунте (14.10.2026):
>
> | подпись | результат |
> |---|---|
> | `Stars` | `PEER_FLOOD` |
> | `⭐` | `PEER_FLOOD` |
> | `XTR` | OK |
> | `Ѕtarѕ` | OK |
>
> Поэтому по умолчанию стоит гомоглиф `Ѕtarѕ`: клиент рисует его как
> обычное «Stars», но строковый фильтр Telegram не узнаёт. Вариант `XTR`
> выглядит честной латиницей и тоже проходит — переключается строкой
> `STARS_LABEL=XTR` в `.env`. Гомоглифы в остальных словах карточки
> остаются в любом случае.

### После отклонения

```html
<b><tg-emoji emoji-id="5260342697075416641">❌</tg-emoji> Пpeдлoжeниe oтклoнeнo.</b>
```

Клавиатура снимается полностью.

> В исходном ТЗ разметка была `<b><tg-emoji emoji-id="..."></b></tg-emoji>` —
> тег `<tg-emoji>` закрывался через `</b>`. Это невалидный HTML: Telegram
> ответит `can't parse entities`. В проекте использован корректный вариант
> `<b><tg-emoji emoji-id="...">❌</tg-emoji> Предложение отклонено.</b>` —
> визуально идентичен.

> **Кому предлагается подарок.** Кнопку «Передать» нажимает продавец, а
> получателем считается: явный `@username` из команды → username того, кто
> нажал «Принять» (это и есть покупатель) → `TRANSFER_RECIPIENT_USERNAME`.
> Если username так и не нашёлся, кнопка ведёт на страницу самого подарка.

> **О deep link `tg://send_gift`.** Это не документированный официальный
> deep link Telegram — клиент либо откроет диалог, либо ничего не сделает.
> Значение вынесено в `TRANSFER_DEEP_LINK`, поэтому его можно заменить, не
> трогая код. Гарантированно рабочие альтернативы:
> `tg://user?id={id}`, `https://t.me/{username}`, `tg://resolve?domain={username}`.

### Рекомендации по оформлению

- **Экранируйте всё пользовательское.** `app.utils.text.esc()` для текста и
  `esc_attr()` для атрибутов — иначе подарок с `<b>` в названии сломает разметку.
- **Не злоупотребляйте `tg-emoji`.** 3–4 эмодзи на сообщение — предел; дальше
  сообщение перестаёт читаться.
- **Разделитель разрядов** — запятая (`382,938`), как в интерфейсе Telegram.
- **Ник автора** выводится обычным текстом, без `@` и без гиперссылки: так
  карточка не выглядит «упоминанием» и меньше рискует попасть под антиспам.
  Хелпер `app.utils.text.user_mention()` доступен, если понадобится ссылка
  `tg://user?id=...` (работает и для аккаунтов без публичного username).

### Обфускация гомоглифами

Текст карточек, который видит покупатель, набран латинскими омоглифами
кириллицы (`app/constants.py`, константы с префиксом `H_*`):

```
Пользователь  ->  Пoльзoвaтeль
за подарок    ->  зa подapoк
```

Подмена **обратима**: тест проверяет, что обратная замена латиницы в кириллицу
возвращает читаемый русский текст.

Подписи кнопок — исключение, они остаются обычной кириллицей:

```
Пpиняtь  ->  Принять
Oтkлoниtь  ->  Отклонить
```

Причина в том, что подпись видна сразу при нажатии: подмена бросается в глаза,
а на антиспам-фильтр Telegram подпись кнопки не влияет. Служебные подсказки,
`/help` и админ-панель тоже обычным русским — их читает продавец.

### Эмодзи на кнопках

В **тексте кнопки HTML не поддерживается** — `<tg-emoji>` там показывается как
обычный текст. Поэтому эмодзи на кнопке задаётся отдельным полем
`icon_custom_emoji_id`:

| Элемент | `emoji_id` | Где задаётся |
|---|---|---|
| Кнопка «Отклонить» | `5260342697075416641` | `icon_custom_emoji_id` |
| Кнопка «Принять» | `5260416304224936047` | `icon_custom_emoji_id` |
| Начало карточки «продан» | `5875180111744995604` | `<tg-emoji>` в тексте |

Кастомные эмодзи в **тексте** требуют Telegram Premium у владельца бота. Без
подписки (или при сбое на стороне Telegram) приходит
`Bad Request: ENTITY_TEXT_INVALID` — и Telegram отвергает **весь запрос**, а не
только тег, то есть карточка «продан» просто не ушла бы. Поэтому шлюз на такой
отказ повторяет тот же запрос, а если отказ повторился — заменяет теги обычными
символами (`🎁`, `❌`). Жирный текст и ссылки при этом сохраняются: снимается
только премиум-обёртка, а не весь `parse_mode`.

## 9. Сохранение бизнес-подключений

### Почему подключение «исчезает»

Telegram присылает событие `business_connection` **ровно один раз** — в момент
подключения. Если в этот момент бот не работал (перезапуск, поллинг офлайн,
свежая база), событие теряется навсегда. Дальше каждый апдейт приходит с
`business_connection_id`, которого нет в базе.

Прежний код в этом случае тихо откатывался на отправку от имени бота:

* карточка уходила не от бизнес-аккаунта;
* команду удалить было нечем (`bot_access_forbidden`);
* `/business_info` показывал «Подключений пока нет».

Со стороны это выглядит как «команда проигнорирована».

### Где брать состояние подключения

| Задача | Метод Bot API |
|---|---|
| Узнать подключение и его права | `getBusinessConnection(business_connection_id)` |
| Отправить от имени аккаунта | `sendMessage` + `business_connection_id` |
| Отредактировать / удалить | `editMessageText` / `deleteBusinessMessages` + подключение |
| Ответить на кнопку | `answerCallbackQuery` **без** подключения |

`business_connection` приходит один раз, поэтому состояние всегда уточняется
через `getBusinessConnection` — это единственный источник настоящих прав. Из
апдейта их не узнать, а без них нельзя объяснить, почему отправка не проходит.

### Что сделано

При старте бот переспрашивает все подключения и пишет в лог их состояние и
права (`app/services/business.py`). Если прав нет ни одного — `WARNING` с
прямым указанием, что делать.

`business_connection_id`, а **восстанавливает запись** — сначала через
`getBusinessConnection` (возвращает настоящие права), а если сеть недоступна —
запасным путём из самого апдейта (`register_from_update`). Владелец известен:
`business_message` по определению отправлен подключённым аккаунтом, поэтому его
`from_user` — и есть владелец подключения.

Отключённое подключение так не восстанавливается: пользователь отключил бота
осознанно, и молча игнорировать его решение нельзя.

Значение `DEFAULT_BUSINESS_CONNECTION_ID` из `.env` тоже проверяется по базе —
раньше невалидный идентификатор в конфигурации проходил мимо проверки и ломал
отправку.

### Про удаление команды

`deleteBusinessMessages`, а не `deleteMessage` + `business_connection_id`:
параметр появился в Bot API 9.0, и текущая версия aiogram его ещё не
поддерживает. Практическая разница видна сразу — без подключения удалить
команду не удаётся (у бота нет доступа к чужому личному диалогу), и вместо
карточки пользователь видит «команда проигнорирована».

## 10. Карточка не доходит: `BUSINESS_PEER_INVALID`

### Что означает

Telegram не дал боту написать в чат от имени бизнес-аккаунта. Причин две:

1. **Нет права «Разрешить отвечать на сообщения».** При подключении бота надо
   отметить все галочки. Без них подключение выглядит рабочим — бот пишет
   «подключён» — но отправлять от имени аккаунта он не сможет.
2. **В диалоге не было входящих сообщений последние 24 часа.** Telegram
   разрешает боту писать от имени аккаунта только в активные личные чаты.
   Покупателю писать боту при этом не нужно — ограничение на стороне аккаунта.

### Что сделано

| Проблема | Решение |
|---|---|
| Права не выданы — карточка не шла | Откатная отправка: при `BUSINESS_PEER_INVALID` карточка уходит **от имени бота** — сделка состоится, пока права не выданы |
| Объясняли следствие, а не причину | `BusinessFallbackFailed` сохраняет **первую** ошибку; иначе советовали «написать боту /start» вместо прав аккаунта |
| Причина была только в логе | Отдельная подсказка `hint_business_peer` на ru/en/ar с конкретными шагами |
| Объяснение не доходило никуда | Цепочка доставки: чат → аккаунт продавца → бот → продавец |
| Подключение без прав выглядело рабочим | `WARNING` при подключении вместо `INFO` |

Понижение выполняется один раз: если и от имени бота Telegram отказал, пробовать
дальше бессмысленно, и причина уходит продавцу цепочкой: чат → аккаунт продавца →
бот → продавец.

Ответ на кнопку (`answerCallbackQuery`) отправляется **без**
`business_connection_id` — так требует Bot API. Это закреплено тестом.

## 11. Сообщение «висит», а ответа нет

Симптом: команда отправлена, в чате крутятся часики, бот не отвечает — ни
когда, ни потом.

### Почему так

Не-админ отбрасывается гейтом `AdminGateMiddleware` **молча**: по требованию
бот не реагирует ни на команды, ни на подключение бизнес-аккаунта. Для
постороннего это неотличимо от зависания — ответа не будет никогда, и ждать
бессмысленно.

Частая причина — не тот ID в `OWNER_IDS`. Свой Telegram ID невозможно
вычислить в уме, а именно он нужен владельцу.

### Что сделано

1. **`/id`** — отвечает **любому**, включая посторонних: возвращает ID,
   юзернейм и роль, а если доступа нет — подсказку `/add_admin <ваш ID>`.
   Это единственная команда, которую бот выполняет для не-админов
   (`PUBLIC_COMMANDS` в `app/middlewares/__init__.py`). Силуэт бота при этом
   не раскрывается: посторонний узнаёт только свой ID и отсутствие доступа.
2. **Лог гейта actionable.** Вместо `Апдейт от не-админа отброшен: user=…`
   пишется, что делать: `— выдать права: /add_admin 7252499710`.
3. **Стартовый лог.** При запуске выводится `Владельцы (OWNER_IDS): …`, а если
   список пуст — предупреждение. Сразу видно, что бот запущен не для того
   аккаунта.

### Если «виснет» админ

Тогда дело не в правах, и стоит проверить:

| Причина | Признак в логе |
|---|---|
| Нет бизнес-подключения | `benz отклонена: … не владелец бизнес-подключения` |
| Подключение отключено | `business_connection_id … не найден или отключён` |
| Антифлуд | `Антифлуд: сообщение от … отброшено` (уровень `DEBUG`, включить `LOG_LEVEL=DEBUG`) |
| HTML/кнопки не прошли | `Кнопки упрощены` / `HTML не распознан` — запрос уходит повторно, безопасно |

Собственный сценарий (`benz` в личке с ботом, без бизнес-подключения)
покрыт E2E-тестом: карточка уходит, кнопки на месте.

## 11. `RECORD_LAYER_FAILURE` / `ClientConnectorSSLError`: сеть, а не код

Симптом: бот стартует, версию и владельцев печатает, но каждый запрос к
Telegram обрывается на TLS, а в логе идут повторы 5 → 10 → 20 с.

```
Не удалось снять webhook (продолжаю polling): ClientConnectorError
Не удалось получить профиль бота (сеть недоступна): ClientConnectorSSLError
  [[SSL: RECORD_LAYER_FAILURE] record layer failure]
```

Это **не** ошибка бота, токена или прав. DNS резолвится, TCP до 443 соединяется,
но TLS-хендшейк ломается — классический признак, что соединение перехватывают
(DPI провайдера) или режет локальный прокси.

### Самая частая причина: VPN в режиме «системного прокси»

Ваш VPN (xray, v2ray, Neocor и подобные) слушает локальный порт и прописывает
его в настройки Windows. Браузер это уважает, а **aiogram — нет**: по
умолчанию он системный прокси не читает и идёт напрямую, где вас режут.

Проверка (PowerShell):

```powershell
Resolve-DnsName api.telegram.org                 # DNS
Get-NetTCPConnection -State Listen -LocalPort 10809   # кто слушает прокси
curl.exe -o NUL -w "%{http_code}" --proxy 127.0.0.1:10809 https://api.telegram.org
curl.exe -o NUL -w "%{http_code}" --noproxy "*"           https://api.telegram.org
```

Через прокси должен быть `302`, напрямую — `000`. Значит, дело точно в прокси.

Решение — указать прокси боту явно:

```env
TELEGRAM_PROXY=http://127.0.0.1:10809
```

Порт узнаётся командой выше (у xray это обычно 10809 — HTTP и 10808 — SOCKS;
`AiohttpSession` работает с HTTP, поэтому нужен именно тот, что отвечает на
HTTP). Альтернатива без правки конфига: переключить VPN в режим TUN/redirect,
тогда весь трафик, включая прямые сокеты, пойдёт через него.

## 12. Отзывчивость

Очередь апдейтов у бота общая, поэтому любое ожидание в обработчике — это
задержка **следующей** команды. Отсюда четыре решения.

### 1. Команда удаляется до отправки карточки

Порядок именно такой: `deleteBusinessMessages` → `sendMessage`. Раньше было
наоборот, но только ради `reply_to_message_id`, который больше не
используется. Теперь в чате не мелькает сырой текст «benz …», а карточка
появляется сразу.

### 2. Тост уходит до редактирования

`answerCallbackQuery` вызывается сразу после атомарного `claim`, а
`editMessageText` — следом. Клиент перестаёт крутить спинмер не дожидаясь
round-trip за текстом карточки.

### 3. Уведомление продавцу уходит фоновой задачей

Оно не должно задерживать редактирование у покупателя, поэтому запускается
через `asyncio.create_task`. Ссылка на задачу хранится в `_BACKGROUND_TASKS`,
иначе сборщик мусора может отменить её на полпути.

### 4. Короткие паузы при флуд-лимите

Раньше повторы шли по экспоненте: 3 → 9 → 27 с. Суммарно почти полминуты
заблокированной очереди — и каждая следующая команда ждала этого.

| | было | стало |
|---|---|---|
| Паузы | 3 → 9 → 27 с | 0.4 → 1 → 2 с |
| Потолок `retry_after` | 30 с | 5 с |
| `OFFER_THROTTLE_SECONDS` | 1.0 | 0.5 |

Пейсинг не выбрасывает команды: лишние ждут своей очереди и всё равно
обрабатываются. Значение больше секунды больше не «теряет» второе
предложение — подождать придётся, но карточка придёт.

### 5. Одна команда — одна карточка

Telegram доставляет апдейты по схеме «хотя бы один раз» и может прислать один
и тот же `benz` повторно — например, после перезапуска бота до подтверждения
`offset`. Раньше это давало 2–3 одинаковые карточки: каждая повторная
доставка создавала новую сделку.

Теперь у предложения есть `command_key` (источник + чат + `message_id`) с
уникальным индексом, а вставка идёт через
`INSERT … ON CONFLICT(command_key) DO NOTHING`. Повторная доставка не создаёт
вторую сделку и не шлёт вторую карточку; если первая карточка не успела уйти
(`message_id` пуст), она досылается по уже существующей сделке. Это же
защищает от запущенного по ошибке второго инстанса бота.

### 6. Общий тормоз после флуд-лимита

Пейсинг в пределах одного пользователя не спасает от пачки: десять команд от
десяти разных людей всё равно уходят в Telegram залпом и получают 429. Поэтому
в `app/services/telegram.py` есть `FloodGuard` — общий тормоз на весь бот:

* как только Telegram ответил «флуд», любая следующая команда выдерживает паузу
  независимо от автора;
* повторные флуды увеличивают паузу (×2, ×4), потолок — 10 с;
| | было | стало |
|---|---|---|
| Реакция на 429 | пауза только у этого запроса | пауза у всех команд бота |
| Рост паузы | нет | ×2 → ×4, потолок 10 с |

Пауза всегда конечна: её задаёт `retry_after` от Telegram, а не «пережидание»
лимита. Успешная отправка сбрасывает счётчик роста, но уже назначенную паузу
не отменяет — лимит считается на аккаунт.

### Если карточку не удалось отредактировать

Вместо тишины бот отправляет её заново новым сообщением: покупатель в любом
случае видит результат.

### Про параллельность

Апдейты обрабатываются пулом задач с ограничением
(`tasks_concurrency_limit=24`): пачка команд не бьёт в Telegram залпом и не
ловит `429`. Гонки при этом закрыты: вставка сделки идемпотентна по
`command_key`, а нажатие «Принять» разрешает атомарный `claim` — второе
нажатие видит уже закрытую сделку.

## 14. Замечания по архитектуре

**Роутеры создаются фабриками** (`create_offer_router()` и т. д.), а не
объявляются на уровне модуля. Экземпляр `Router` в aiogram можно подключить
только к одному `Dispatcher` — при повторной сборке (тесты, перезагрузка)
модульные роутеры падают с `RuntimeError: Router is already attached`.

**`TelegramGateway`, а не голый `bot`.** Любой исходящий вызов проходит через
слой с тремя уровнями деградации: сначала снимается оформление кнопок, затем
HTML-разметка. Пользователь никогда не увидит «зависший» бот из-за одного
неподдерживаемого параметра.

**Антифлуд изолирован в роутере `benz`.** Он гасит спам командами, но
намеренно пропускает `CallbackQuery` — иначе пользователь не смог бы нажать
«Принять» в том же интервале, и это выглядело бы как зависший бот.

**Срок действия проверяется в SQL**, а не в Python: это защищает и от гонки,
и от «забытого» фонового таймера. Просроченные предложения просто перестают
быть доступны для принятия.
